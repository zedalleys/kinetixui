# Motion Lab — five-platform implementation contract

**Status: React is implemented. Angular, SwiftUI, Jetpack Compose and Flutter are SPECIFIED AND NOT
IMPLEMENTED.** Nothing in this document is evidence that a native platform does any of it. It exists so that
a platform which later adopts the travelling indicator has a written contract to be measured against, rather
than a React screenshot to imitate.

This is not a certification document and does not change any promotion status. `selection-indicator` is
`observed` in `tokens/contracts/motion.json`, with React's `Tabs` as its only consumer, and this repository
promotes a role to `proven` on a **second platform consuming it**. That status is left exactly as it is.
What follows is the specification such a second consumer would have to satisfy; writing it down is not
consuming it.

Source of the React behaviour: `apps/web/src/lib/motion-lab/use-track-indicator.ts`, measured by
`scripts/motion-lab-browser.mjs`. Every number below is a token name, never a literal.

---

## 1. The interaction contract

One indicator belongs to one track. The track owns a set of items, exactly one of which is chosen. The
indicator's only job is to show **which item is chosen**, and it is never the only thing that shows it.

| | |
|---|---|
| **Trigger** | A change of the chosen item, from any source: pointer, keyboard, programmatic, or a restored value. |
| **Not a trigger** | A re-activation of the already-chosen item; a resize; a reflow; a font arriving; a direction or orientation change. Each of those is a **re-placement**, below. |
| **Owner of the value** | The host component, never the indicator. The indicator reads the chosen item; it never decides it. |
| **Owner of the geometry** | The indicator, measured from the chosen item's own box at placement time. Never a stored index multiplied by an assumed item width. |

A **travel** is a change of chosen item while the previous one was known. A **snap** is every other
placement: the first placement, a re-frame (direction or orientation changed), a resize, and any placement
made while motion is reduced. A snap is not a zero-duration travel — it must not interpolate at all, because
an indicator that eases across during a window drag reads as the selection moving by itself.

## 2. Tokens

| Purpose | Token | Value today |
|---|---|---|
| Travel duration | `--duration-base` / `duration.base` | 300ms |
| Phased hold, trailing edge | `--duration-base` | 300ms |
| Crossfade in and out | `--duration-fast` | 200ms |
| Travel easing (default) | `--easing-emphasized` | `cubic-bezier(0.2, 0, 0, 1)` |
| Travel easing (phased) | `--easing-standard` | `cubic-bezier(0.4, 0, 0.2, 1)` |
| Fade out | `--easing-exit` | `cubic-bezier(0.4, 0, 1, 1)` |
| Fade in | `--easing-enter` | `cubic-bezier(0, 0, 0.2, 1)` |

A platform that cannot express a cubic Bézier directly must convert from these four control points and say
so in its own source; it may not substitute a named system curve and call it the same motion. **No platform
may introduce a duration this table does not contain.** The lab's variant switch chooses between behaviours
composed from these tiers; it cannot set a duration, and neither may a native port.

**The spring is not in this table, and that is deliberate.** `MOTION.md` records that no component uses a
spring and that springs are not tokens. The lab's damped spring
(`apps/web/src/lib/motion-lab/spring.ts`: stiffness 320, damping 36, mass 1, ζ ≈ 1.006) is an **instrument**
— it exists to show what velocity continuity feels like against the three transition variants, and to give
the interruption measurements something to compare. A platform porting the indicator ports the **transition**
variants. Adopting the spring would be a token proposal, with an owner decision, not an implementation
detail.

## 3. State ownership and retargeting

The engine keeps five pieces of state, and a port needs all five or it cannot satisfy §4:

| State | Why it cannot be dropped |
|---|---|
| `chosen` — the item last placed on | Distinguishes a travel from a snap. Without it every placement animates. |
| `start`, `end` — the logical insets last written | Lets a placement detect that nothing moved and return. |
| `frame` — orientation and direction | A change here is a re-frame, which must snap, not travel. |
| the live animation handle | A retarget must be able to act on the animation that is already running. |
| `spring` position and velocity (spring variant only) | Velocity is what a transition cannot carry. |

**Retargeting is the hard requirement.** If the indicator is travelling to B and the reader chooses C, the
new motion starts **from the position currently rendered**. It may not reset to A, and it may not jump to B
first. The two mechanisms differ in what they can carry, and a port must state which it has:

- **A platform transition** (CSS transition, SwiftUI `withAnimation`, Compose `animateDpAsState`, Flutter
  implicit animation) restarts from the **current computed value**, so position is carried and **velocity is
  not**: the indicator decelerates to a halt at the boundary and accelerates again. That is acceptable and is
  what every transition variant does.
- **An integrated animation** (the lab's rAF spring, a Core Animation additive animation, a Compose
  `Animatable.animateTo` on a running `AnimationVector`) carries position **and** velocity.

**A note on how that difference is and is not evidenced.** An earlier version of this document quoted
measured retention percentages from the browser gate. They have been removed, because the measurement did
not support them: a retarget takes effect about four frames after the interaction (React's commit plus a
`MutationObserver`), so a window taken either side of the interaction falls on the same pre-retarget curve
and reads the variant's own deceleration. Velocity carry is asserted where time can be controlled exactly —
`apps/web/src/lib/motion-lab/spring.test.ts`, "carries an initial velocity instead of discarding it". A
native port should assert it the same way, in its own unit layer, and should not try to prove it from
sampled frames.

What is *not* acceptable on any platform is re-seeding the animation from the stale logical origin. The lab
expresses this as a single rule: **hand the running animation a new target; never re-create it.** Negative
control 2 in `scripts/motion-lab-negative-controls.mjs` restores the re-seeding defect and is required to
turn the interruption section red.

## 4. Acceptance, per platform

A port is complete when each row is measured on that platform. "React" is the only column with evidence.

| # | Requirement | React |
|---|---|---|
| 1 | A travel renders intermediate positions in both directions | 19 distinct offsets forward and back |
| 2 | A travel never reverses direction | measured over every sampled frame |
| 3 | A travel settles on the chosen item's box | within 1.5px |
| 4 | A retarget continues from the rendered position | boundary step within the run's own worst normal frame |
| 5 | A retarget never returns to the origin box | whole box, not one edge |
| 6 | A retarget never visits the abandoned destination | asserted |
| 7 | The integrated retarget carries velocity | asserted in the integrator's unit suite, not from sampled frames — see the note in §3 |
| 8 | Reduced motion renders no intermediate position | ≤2 offsets |
| 9 | Reduced motion reaches the **end** state, not a midpoint | within 1.5px |
| 10 | A reduced-motion preference cannot be overridden from the page | the override is one-way |
| 11 | RTL mirrors: a later item is reached by moving the other way | measured in both directions |
| 12 | The chosen state is announced on the interaction, not after the motion | 3.7–8.5ms, while still travelling |
| 13 | Exactly one item is chosen at every sampled frame | asserted per frame |
| 14 | Focus stays visible, and keeps its ring, across a travel | measured |
| 15 | A disabled item is skipped by roving focus and cannot be chosen | measured |
| 16 | Under forced colours the indicator gives way to the system selection pair | measured |
| 17 | Nothing keeps running once a travel settles | 30 idle frames, one offset |
| 18 | A re-placement that does not change the selection does not interpolate | resize measured |
| 19 | Rapid alternation ends on the item chosen **last** | measured |
| 20 | No part of the indicator is reachable by keyboard or present to a screen reader | measured |

## 5. Per-platform notes

### Angular — closest port, no blocker

`packages/ui-angular/src/lib/tabs.ts` renders panels and triggers with no indicator element at all, so this
is an addition rather than a change. Angular's DOM is the same DOM: the engine's logical insets, its
`ResizeObserver` and `MutationObserver` placement triggers and its forced-colours rule all transfer
unchanged. Two Angular-specific points: placement must run outside change detection (it writes style
properties, not bindings, so it must not trigger a cycle), and the direction read must come from the
element's computed `direction`, not from an injected locale, so a nested `dir` is honoured.

**This is the cheapest route to a second consumer**, which is what `selection-indicator` needs for promotion.
It is not proposed here; it is costed here.

### SwiftUI — `matchedGeometryEffect`, and one real constraint

`SegmentedControl.swift` draws the chosen segment as a filled surface with no travel
(`selection-state`, not `selection-indicator`). The idiomatic port is one `matchedGeometryEffect` namespace
with the indicator as the source on the chosen segment. Two constraints that must be written into any
proposal rather than discovered during it:

1. `withAnimation` honours `accessibilityReduceMotion` only if the code reads it; it is not automatic. The
   reduced form is `remove-travel`, which in SwiftUI means placing without an animation block, not a
   `.animation(nil)` modifier on the container.
2. `matchedGeometryEffect` re-interpolates from the current frame on a retarget, so it satisfies
   requirement 4 but not 7. A SwiftUI port therefore implements the **transition** variants and must not
   claim the spring's velocity continuity.
3. The existing SwiftUI Sheet VoiceOver focus blocker is a **separate** matter and remains REQUEST CHANGES.
   Nothing here touches `Sheet.swift` and no part of this specification depends on that blocker being
   resolved.

### Jetpack Compose — the one platform that can satisfy all 20

`Tabs.kt` has no indicator. Compose is the only target that can meet requirement 7 as written, because
`Animatable.animateTo` on a running animation carries its `AnimationVector`'s velocity through a retarget by
design — so a Compose port could legitimately adopt either family. `LocalLayoutDirection` gives RTL for free
if offsets are expressed as `start`/`end` rather than `x`. The reduced-motion read is
`LocalAccessibilityManager`/`Settings.Global.ANIMATOR_DURATION_SCALE`; a scale of 0 must take the snap path
rather than running a 0ms animation, because a 0ms animation still emits a frame and still fires listeners.

### Flutter — watch the implicit-animation trap

`tab_bar.dart` has no travelling indicator. Flutter's `AnimatedPositioned`/`AnimatedContainer` restart from
the current value on a retarget, which satisfies requirement 4. Requirement 18 is where Flutter ports
usually fail: an implicit animation animates **any** change to its target, including the one a `LayoutBuilder`
produces on a resize, so a Flutter port needs the same explicit "did the selection change" decision the
engine makes — not an implicit widget alone. `MediaQuery.disableAnimations` is the reduced-motion read, and
`Directionality` gives the mirror.

## 6. What this document does not do

- It does not claim any native implementation exists. Four of the five columns in §4 are empty.
- It does not change `tokens/contracts/motion.json`, `motion-consumers.json`, `verification.json` or
  `platform-parity.json`, and it does not alter `selection-indicator`'s `observed` status.
- It does not propose adopting the spring. That needs a token decision.
- It does not touch PRs #645–#650, the frozen native motion stack, or `Sheet.swift`.
