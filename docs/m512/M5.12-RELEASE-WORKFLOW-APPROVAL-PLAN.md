### What I could not determine, and am not guessing

Both green and gated heads are commits authored *and* committed by `github-actions[bot]`
(`chore: version packages`), and the green runs show `actor: zedalleys` **and**
`triggering_actor: zedalleys` with `run_attempt: 1` and `run_started_at == created_at`. An approved
run would show the original actor, so these were **not** approvals of gated runs — they were created
with that attribution from the start.

The two candidate mechanisms I could not distinguish:

1. `release.yml:174` reads `GITHUB_TOKEN: ${{ secrets.RELEASE_PAT || secrets.GITHUB_TOKEN }}`. A push
   made with `RELEASE_PAT` is attributed to that token's owner, which would explain the green heads;
   a fallback to `GITHUB_TOKEN` would explain the gated ones. **But** runs 43731228905 (green head
   `7a252dcf`) and 43731421588 (gated head `7af1793c`) are two runs of the same workflow ninety
   seconds apart with an unchanged workflow file, so the secret cannot have differed between them.
2. A repository or organisation Actions approval setting. **This cannot be read from a cloud session**
   — GitHub GraphQL returns 403 and branch-protection and Actions settings are unreadable — so any
   claim about its value, in either direction, is unverified.

The brief said not to infer the setting from behaviour, and I have not.

## 4. Publication cannot happen by approval or by merge

`release.yml`'s `publish` job is `if: needs.plan.outputs.changesets_pending == 'false'`, carries
`environment: publish-npm`, and its **first** step — before the toolchain is installed — runs
`node scripts/release/approval.mjs --environment=publish-npm`, which reads the approval from the run
itself. The file's own comment explains why: an `environment:` naming an environment that does not
exist, or one whose reviewers were removed, does **not** fail — GitHub runs the job immediately.

I ran that guard against a **real, unapproved run**:

| probe | exit |
| --- | --- |
| no `GITHUB_REPOSITORY` / `GITHUB_RUN_ID` | **1** — "an unidentified run is not an approved one" |
| real repository, nonexistent run id | **1** |
| real repository, the real 17:15 `Release` run 43916396586 (never approved) | **1** — "`publish-npm` must exist with required reviewers configured, and this run must have been approved for it" |
| no token at all | **1** |

So the `publish-npm` reviewer gap is a **stall, not an exposure**, and that is now established by
executing the guard rather than by reading a setting I cannot read. Merging #622 **queues** a
publication; a separate approval performs it; and if the environment is misconfigured the job fails
closed instead of publishing.

**One consequence the owner should weigh separately:** every push to `main` deploys kinetixui.com, and
#622 changes `apps/web/src/lib/releases.ts`. Merging #622 therefore **publishes the 0.28.0 changelog
page to the live site before anything reaches npm.**
