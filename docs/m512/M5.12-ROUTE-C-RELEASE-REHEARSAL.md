## Why Route C works, stated exactly

`scripts/version-release-meta.mjs` activates a curated note only when `releases.ts` does not already
mention the version:

```js
if (!history.includes(`version: "${version}"`)) { … }
```

`main` has no 0.28.0 entry, so the one regeneration picks up **both** corrections. Verified by content,
not by inference: after the rehearsal `apps/web/src/lib/releases.ts` contains the corrected Progress
paragraph (`nested span inside the indicator`) and the audio entry (`documented audio player ships the
clip`).

This is also precisely why the reverse order cannot work. Merge #622 first and `releases.ts` gains a
0.28.0 entry carrying the superseded prose; the guard then suppresses every later activation.

## The drift defect, and the gate now proposed for it

On the regenerated tree, replacing the curated Progress paragraph with a sentinel left
`check:releases`, `check:release-note` and `check:release-note-coverage` all exiting 0. Re-running
`scripts/gen-release-meta.mjs` **also** exited 0 and left `releases.ts` carrying the stale prose,
because the version was already present. So the drift was not merely undetected — it was
**unrepairable by regeneration**. The only repairs are a hand edit or deleting the entry first.

`scripts/check-release-note-sync.mjs` closes it, in **draft PR #638**, and is verified green on `main`
(4 activated notes of 6 match). Six controls, kept as tests in
`scripts/release/test/release-note-sync.test.mjs`, 7/7 passing: a corrected note fails, a hand-edited
page fails, a tree with no notes fails, a date-only difference passes, an unactivated note passes, and
blinding the comparison makes the first failure invisible.

## A second finding: the coverage gate goes vacuous after the recut

Measured on both sides of the same tree.

- **Before** the recut: `check:release-note-coverage ok — release/notes/0.28.0.json covers every
  changeset this release consumes — angular@0…`
- **After** the recut: `check:release-note-coverage ok — no pending changeset moves a published release
  cohort, so no curated note is wanted` and `check:release-note — ok, no pending changeset moves
  @kinetixui/ui; no curated note is wanted`.

Both pass by having nothing to check. **The Version PR's own CI can therefore never validate the note's
coverage.** That is the structural reason a note correction has to land before the recut rather than
being argued about afterwards, and it is independent of #622's stranded workflows.
