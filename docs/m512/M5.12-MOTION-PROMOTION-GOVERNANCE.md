# M5.12 — Motion promotion governance

**Verdict: PASS.** The defect is reproduced, the repair is built and controlled, and it is offered as
**draft PR #639**. Nothing was promoted. The owner has not approved promotion to `proven` and the
register records `selection-indicator` as `pending`.

## The defect, reproduced

On the four-platform `selection-indicator` reconciliation candidate, with `check:motion-tokens`,
`check:native-motion`, `check:motion-identity-controls` and `check:motion-ledger-controls` all green:

| mutation | outcome |
| --- | --- |
| `status` changed `observed` → `proven` | **all four exit 0.** A silent promotion passed every motion gate in the repository. |
| the sentence recording the rule as TRIGGERED deleted from the role's note | **all four exit 0.** |

The second matters because that sentence was the only written trace of the pending decision, and four
of the open `selection-indicator` branches each rewrite that note — so any of them could have removed
it as a side effect of a merge resolution.

### One correction to the received picture

On **`main`**, `selection-indicator` has exactly **one** consumer (`react`) and its note does **not**
contain the word `TRIGGERED`. The rule is not yet triggered there, and there is nothing to delete. The
trigger sentence and the second platform arrive together, with #628. So the exposure is a property of
the recovery stack, not of `main`.

## The repair

`tokens/contracts/motion-promotions.json` — a machine-readable decision record whose only purpose is
authorisation — plus `scripts/check-motion-promotion.mjs`, which holds it against
`tokens/contracts/motion.json`. The brief's eight requirements, each as implemented:

| # | requirement | how |
| --- | --- | --- |
| 1 | identify roles with multiple registered consumers | distinct **platforms** ≥ 2, because `selection-state`'s three React files are one platform. The threshold is the repository's own written rule: "promotes a role to proven on a SECOND platform consuming it". |
| 2 | preserve triggered-review vs approved-promotion | `state: "pending"` vs `state: "approved"`; `$states` in the file defines both. |
| 3 | reject unauthorised `observed` → `proven` | `proven` requires `state: "approved"`; a `pending` decision with `status: proven` fails, naming the legitimate route. |
| 4 | detect deletion or contradictory replacement | a triggered role with no entry fails; a decision for a role the contract does not define fails; a decision for a single-platform role fails; `approved` without `approval.authority`, or with a `basis` under 40 characters, fails. |
| 5 | avoid fragile exact-sentence matching | the record is JSON. **A control asserts that rewording the note PASSES** — an earlier draft of this gate matched the sentence, which passes on a note that contradicts itself in the next sentence and tells a branch to add a word. |
| 6 | allow legitimate future promotion | set the decision to `approved` with an authority and a basis in the same change. A control exercises exactly that and passes. |
| 7 | avoid blocking unrelated roles | single-platform roles need no entry; controls add both an unrelated single-platform role and an unrelated two-platform role with its decision, and both pass. |
| 8 | preserve existing valid registrations | the decision's `platforms` must equal the contract's, so a dropped **or** an added consumer fails. Every `evidence` path a role cites must exist. |

### What is recorded, and what is not

| role | platforms | status | decision |
| --- | --- | --- | --- |
| `selection-control` | 5 | `proven` | `approved`, authority **`pre-existing-on-main`** |
| `disclosure` | 5 | `proven` | `approved`, `pre-existing-on-main` |
| `selection-state` | 5 | `proven` | `approved`, `pre-existing-on-main` |
| `press-feedback` | 2 | `proven` | `approved`, `pre-existing-on-main` |
| `loop` | 5 | `proven` | `approved`, `pre-existing-on-main` |
| `overlay` | 2 | `observed` | **`pending`** — newly surfaced |
| `selection-indicator` | 4 (on the stack) / 1 (on `main`) | `observed` | **`pending`** |

`pre-existing-on-main` documents a status that shipped before the register existed. It is deliberately
**not** written as an owner approval, and the `basis` text says so.

**`overlay` was surfaced by writing the register.** It has had two platform consumers (`react`,
`angular`) and `status: observed` with no recorded decision, so the rule was already triggered and
nothing said so. Its single evidence file covers React only; Angular's side has no evidence entry. No
promotion is proposed — it is recorded as `pending` with the open question stated.

## Negative controls

`node scripts/motion-promotion-negative-controls.mjs` — **18 controls, 12 refusals and 6 allowances**,
every one mutated in memory over a deep copy, so nothing on disk is touched and nothing needs
restoring. Anchors are **derived from the files** rather than named, so a contract that moves on makes
the suite refuse to run instead of quietly testing nothing.

The six the brief required, and the outcome observed:

| required control | observed |
| --- | --- |
| unauthorised status promotion | **FAIL** — "status is `proven` while … still records the decision as `pending`" |
| removal of the required pending-decision record | **FAIL** — "consumed by 4 platforms … with no entry" |
| dropped registered consumer | **FAIL** — "the decision records platforms […] but motion.json registers […]" |
| invalid evidence reference | **FAIL** — "evidence `…` does not exist" |
| legitimate unchanged `observed` | **PASS** |
| legitimate records for unrelated roles | **PASS** (both the single-platform and the two-platform case) |

Twelve more, all behaving: an emptied register, an **added** consumer without revisiting the decision,
an approval with no authority, an approval whose basis restates the status, a pending decision with an
empty review, a decision for an undefined role, a decision for a single-platform role, a
single-platform role promoted, the tree as it stands, the note reworded, and a legitimate promotion.

## Deployment, and a sequencing result worth having

Measured both ways:

- The register **as written for the stack** fails on plain `main`: `✗ selection-indicator: … holds a
  decision for it, but motion.json registers 1 platform(s)`.
- The register **minus the `selection-indicator` entry** passes on plain `main`:
  `check:motion-promotion ok — 6 roles consumed by two or more platforms, 5 approved and 1 pending`,
  with all 18 controls still correct and `check:motion-tokens`, `check:motion-identity-controls`,
  `check:motion-ledger-controls`, `check:native-motion` and `check:registry-motion` all still green.

So the better route is the second: **land the register on `main` now, without a `selection-indicator`
entry.** Then the branch that adds the second platform — #628 — cannot merge without recording the
decision. That is the governance working by construction rather than by reminder, and it is what
PR #639 contains.

## What this does not do

It cannot stop a determined change: a branch may set a decision to `approved` and promote in the same
commit. What it removes is the **silent** promotion. A promotion is now a visible edit to a
single-purpose file, carrying a named authority and a checkable basis, in a diff a reviewer reads as
what it is. Stating that limit is part of the repair, not a caveat on it.
