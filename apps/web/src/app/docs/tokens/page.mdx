# Tokens

KinetixUI's design decisions (colour, spacing, radius, type, motion) live in one set of DTCG token files.
Style Dictionary compiles them into each platform's own idiom: CSS custom properties and a typed object for
the web, Swift for iOS, Kotlin for Android and Dart for Flutter. The generated files are committed, so you
can read every platform's output without building anything.

Tokens are generated; components are not. Each platform's components are written natively against the same
token contract, which is why a SwiftUI button behaves like a SwiftUI button. See [Platforms](/docs/platforms)
for what is implemented where.

## Architecture

```text
tokens/**/*.json            DTCG source: the only place a value is written
  │
  ▼  style-dictionary/build.mjs   (Style Dictionary, once per theme)
  │
packages/tokens/dist/
  ├─ web/       CSS custom properties + typed TypeScript object
  ├─ ios/       Swift
  ├─ android/   Kotlin + Android XML resources
  └─ flutter/   Dart
```

The source is organised in two layers:

```text
tokens/
├─ primitives/
│  ├─ color.json        6 brand ramps + azure action ramp + synthesized neutral, 0–1000
│  ├─ dimension.json    spacing, radius, border width
│  ├─ typography.json   Material-3 scale, Montserrat
│  ├─ motion.json       duration + easing (cubicBezier)
│  ├─ opacity.json      hidden/disabled/muted/visible scale
│  ├─ interaction.json  target size, focus ring, press, drag threshold
│  └─ z-index.json      base/raised/docked/focus/sticky/overlay scale
└─ semantic/
   ├─ color.light.json  aliases → semantic contract
   ├─ color.dark.json   the same names, dark values
   ├─ shadow.json       elevation + focus ring (+ shadow.dark.json)
   └─ typography.json   composite text styles
```

All DTCG format (`$value` / `$type`). The palette, spacing and type scale originate in the KinetixUI Figma
file; once a value is in these files it is authoritative, and the dark theme, motion, opacity and z-index
are owned here rather than in Figma ([`TOKENS.md`](https://github.com/zedalleys/kinetixui/blob/main/TOKENS.md)
records every decision).

The build is a repository step, not something you run to use the tokens:

```bash
pnpm build:tokens   # node style-dictionary/build.mjs — maintainers, inside this repository
```

CI runs the same build and fails if the committed output differs from a fresh generation, so a generated
file cannot be hand-edited without the pull request going red.

## Primitive and semantic tokens

**Primitives** are the palette and scales: `color.azure.700`, `spacing.4`, `radius.md`. They say *what* a
value is.

**Semantic tokens** say what a value is *for*: `color.primary`, `color.card`, `color.border`,
`color.ring`. Components read only semantic tokens. A semantic token is usually an alias of a primitive,
which is how two roles can share a value today and diverge later with a one-line change. The light theme's
`primary` and `ring` both resolve to `color.azure.700`; `brand` is the navy `color.blue.500` that `primary`
was moved off when the interactive colour needed more contrast.

The names follow each language's convention and the values follow each platform's colour type: an HSL

same colour. A test resolves every one of them back to the source hex and fails if a platform disagrees.

## Light and dark

Dark is a second set of values for the same semantic names, not a second set of names. `primary` means
"interactive colour" in both themes; only its value changes, from `azure.700` to the lighter `azure.400`
that holds contrast on a dark surface.

Style Dictionary runs **once per theme**, because two files defining the same token path would collide in a
single run. The light pass emits every platform; the dark pass emits the web `globals.dark.css` **and** the
native semantic theme files that need real dark values: `Theme.dark.kt` (Compose),
`KinetixColorsSwiftUI.dark.swift` (SwiftUI) and `kinetix_color_scheme.dark.dart` (Flutter).

On the web, dark applies under a `.dark` ancestor; see [Dark mode](/docs/dark-mode). The semantic
foreground and background pairs components render are checked against WCAG AA contrast in CI
(`check:contrast`, on the resolved source values), in both themes; on iOS, `swift test` repeats the check on
the generated Swift colour sets themselves.

The `KinetixColorsSwiftUI` / `KinetixColorScheme` pairs are **additive**: the older `Theme.swift` /
`app_theme.dart` outputs (light-only, colliding class names) are untouched. See [SwiftUI](/docs/swiftui)
and [Flutter](/docs/flutter) for why.

## Using the tokens

What you can adopt today depends on the platform. Generated output exists for all four; a package you can
install exists for the web only.

| Platform | Generated output | How you get it today | Package registry | Adapter for stock UI |
| --- | --- | --- | --- | --- |
| Web | Yes | `@kinetixui/tokens` from npm | npm | Tailwind preset in `@kinetixui/ui` |
| iOS (SwiftUI) | Yes | Copy the Swift files from `dist/ios` into your project | None: not on Swift Package Manager or CocoaPods | None for stock SwiftUI views |
| Android (Compose) | Yes | Copy the Kotlin files from `dist/android` into your project | None: not on Maven Central | None for stock Material components |
| Flutter | Yes | Copy the Dart files from `dist/flutter`, or depend on `kinetix_ui` from a repository checkout | None: not on pub.dev | `KinetixMaterialTheme`, `KinetixCupertinoTheme` (in `kinetix_ui`) |

### Web

```bash
npm install @kinetixui/tokens
```

Import the stylesheets once, globally. Light is the base; dark applies under a `.dark` ancestor.

```css
@import "@kinetixui/tokens/css";
@import "@kinetixui/tokens/css/dark";
```

Then refer to semantic roles, never to a raw value:

```css
.panel {
  background: hsl(var(--card));
  color: hsl(var(--card-foreground));
  border: 1px solid hsl(var(--border));
  border-radius: var(--radius-control);
}
```

The typed object is `import { tokens } from "@kinetixui/tokens"`. Tailwind projects should use the preset
from `@kinetixui/ui/tailwind.config`, which maps these variables onto Tailwind's scales. The
[Installation](/docs/installation) page covers the other web route, the CLI, which writes the same
variables into your own stylesheet.

This page is built from the repository's current output. The npm package carries the output of its last
release and can trail it in between; the [changelog](/docs/changelog) lists what each release contains.

### iOS, Android and Flutter

The generated Swift, Kotlin and Dart files are real, and they are the same values as the web output. What
does not exist yet is a native package: none of them is on Swift Package Manager, Maven Central or pub.dev.
To use them today you vendor the files: copy them from `dist/ios`, `dist/android` or `dist/flutter`, which
are in the repository and inside the `@kinetixui/tokens` npm tarball. You then update them by copying again.

Two things change that on Flutter. `KinetixMaterialTheme` and `KinetixCupertinoTheme` turn the tokens into a
Material `ThemeData` or a `CupertinoThemeData`, so stock widgets you already use take on the colours, radius
and type scale without any Kinetix widget in the tree; see
[Using KinetixUI without Kinetix widgets](/docs/flutter#using-kinetixui-without-kinetix-widgets). They live
in the `kinetix_ui` package, which is consumed from a repository checkout, not from pub.dev.

SwiftUI and Compose have no equivalent adapter for stock controls yet. Their `KinetixTheme` supplies the
token colours to KinetixUI's own native components; see [SwiftUI](/docs/swiftui) and
[Jetpack Compose](/docs/compose).

## See the tokens in a component

The [Button](/docs/components/button) is the most direct place to watch this token at work. Its primary
variant fills with `action`, which aliases `primary`; its label is `action-foreground`; its keyboard focus is
the `shadow.focus` ring, drawn in the same blue; its corners are the `md` radius and its padding comes from
the spacing scale. On its page:

- **Toggle the site theme** and the fill moves from `azure.700` to `azure.400` with no change to the
  component, because only the token's value changed.
- **Tab to a button** to see the focus ring, and hover or press it to see the fill step down to `action` at
  90% and 85%, values bounded by the contrast check rather than chosen by eye.
- **Open the Code tab and switch platform** to read the SwiftUI, Compose and Flutter implementations. Each is
  written natively, and each reads the same `action` role from its platform's generated tokens.

### Motion and scale

`duration`, `easing`, `opacity`, and `z-index` are theme-independent, like
typography — defined once, the same in light and dark. Each platform's output
groups them into `KinetixDuration` / `KinetixEasing` / `KinetixOpacity` /
`KinetixZIndex` (native — which also get the spatial scale as `KinetixSpacing`
and `KinetixRadius`, see [Foundations](/docs/foundations)) or `--duration-*` / `--easing-*` / `--opacity-*` /
`--z-index-*` custom properties (web), and `packages/ui`'s `tailwind.config.ts`
wires the web ones into real Tailwind utilities — `duration-fast`,
`ease-standard`, `opacity-disabled`, `z-overlay` — used directly in component
source instead of the ad hoc `duration-200` / `z-50` literals components used
to carry. A handful of pre-existing values that don't cleanly match a token
step (e.g. a couple of `opacity-40`/`opacity-60` icon dimmings) are left as
literals with a comment, rather than silently changed to the nearest token.

**Newly defined, not yet consumed by components:** `duration.instant` (100ms) and the `easing.enter`,
`easing.exit` and `easing.emphasized` curves (standard decelerate / accelerate / expressive), plus the
larger spacing steps (`spacing.10`–`spacing.32`, 40–128) and `radius.xxl` (24). They are part of the contract
and generated for every platform, but no component reads them yet and there are no Tailwind utilities for
the new curves — adopting them is incremental, component by component.

### Interaction tokens

Behavioral values, not visual ones — how big a target has to be, how far a
focus ring sits, how a press or a drag reads. Theme-independent, like motion:

| Token | Value | Wired up? |
| --- | --- | --- |
| `interaction.target.minimum` | `44px` | Not yet — WCAG 2.5.5 (AAA) / iOS HIG / Material's converged minimum hit-target size. No component in this package currently has an explicit hit-target smaller than 44px that would benefit without a bigger layout change (`Checkbox`/`Radio`/`Switch`'s ~18–20px visual controls rely on callers wrapping them in a `Label` for the larger click area, the same pattern their Radix primitives assume) — defined for app authors and future components to reach for, not retrofitted here. |
| `interaction.target.default` | `40px` | Not yet — the default a standalone control should target when nothing else constrains its size. |
| `interaction.focus.width` | `1px` | **Yes** — backs the `spread` of every `shadow.focus*` entry's inner layer (`tokens/semantic/shadow.json`), replacing a hardcoded literal. Compiled CSS output is unchanged (still `0 0 0 1px …`). |
| `interaction.focus.offset` | `2px` | Not yet as a token reference — matches the dominant `ring-offset-2` already used across `packages/ui/src/components` (4 of 6 current call sites; the other 2 intentionally use `ring-offset-1` for tightly-bordered controls). Tailwind's `ring-offset-*` utilities are static classes, not CSS-var-driven, so wiring this one needs either a custom Tailwind token or a run of literal replacements — left for a follow-up slice. |
| `interaction.press.opacity` | `0.8` | Not yet — `Button`'s own active state is a color shift (`active:bg-primary/90`), not opacity-based, so there's no current opacity-driven press consumer to point this at. Defined for components that do reach for opacity feedback. |
| `interaction.drag.threshold` | `4` | **Yes** — `KanbanBoard`'s `PointerSensor` `activationConstraint.distance`, via `tokens.interaction.drag.threshold` imported from `@kinetixui/tokens`. Matches the value KanbanBoard already shipped tuned at, not dnd-kit's textbook default of 8 — this token records the deliberate existing value rather than silently changing drag feel. |

Web-only in this slice — none of the native platform ports (`ui-compose`,
`ui-swiftui`, `ui-flutter`) consume `interaction.*` yet.

### Deviations from raw Figma

The build fixes the `Primay` typo, rounds `letterSpacing` float artifacts, and
synthesizes what Figma lacks (`--card`, `--popover`, `--ring`, the neutral ramp,
the dark theme, `radius.lg`, `spacing.7`). Each is documented in `TOKENS.md`
with its rationale.
