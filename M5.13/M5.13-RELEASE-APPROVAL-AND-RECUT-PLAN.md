## 4. Exact approval procedure for the owner

These are steps for **Ziad** to take. None of them was performed here: approving a queued workflow is
on the brief's prohibited list, and no alternative API or credential was used to approve anything.

**To release the four runs already queued on `6dea7bfe`:**

1. Open https://github.com/zedalleys/kinetixui/pull/622 and scroll to the checks box, **or** go to
   https://github.com/zedalleys/kinetixui/actions and filter by branch `changeset-release/main`.
2. Each blocked run shows a banner reading *"This workflow requires approval from a maintainer"* with
   an **Approve and run** button. Press it for each of **CI**, **Accessibility (browser)**,
   **Accessibility (site)** and **Angular package**.
3. Approving is per **run**, not per workflow — four separate approvals.
4. **Approving these four is not authorization to merge #622 and not authorization to publish.** The
   publication step is separately gated by the `publish-npm` environment, and
   `check:release-approval-gate` **PASSES** on the candidate: the npm publication is the only thing
   behind that environment, and it asserts its own approval before publishing.

**If a recut replaces the head**, the four runs above become moot and four new ones appear on the new
head; repeat step 2 against it. Approving the old head's runs first is wasted effort if a recut is the
chosen route, so **decide route first, then approve once**.

**To make the approvals stop recurring**, the repository setting is under
Settings → Actions → General → *Fork pull request workflows* / *Approval for running fork pull request
workflows from contributors*. **I have not read or changed it, and I am not asserting that it is the
cause** — it is simply where that class of setting lives. Changing Actions approval settings is on the
prohibited list for this phase.
