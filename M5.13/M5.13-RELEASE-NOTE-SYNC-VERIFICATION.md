## What it guards

`version-packages` = `changeset version && node scripts/version-release-meta.mjs`. The writer copies
the curated `release/notes/<version>.json` **verbatim** into `apps/web/src/lib/releases.ts` exactly
once, guarded by ``if (!history.includes(`version: "${version}"`))``, stripping `coverage` and stamping
`date` last. Once a note is activated, a later correction to it never reaches the changelog page, and
**re-running the generator cannot repair it** — the guard sees the version already present and does
nothing.

`scripts/check-release-note-sync.mjs` re-runs the real writer in a scratch directory rather than
parsing the activated TypeScript, then compares, normalising only `date`. It reports the **first
differing character** with a window of context, because a first-differing-*line* diagnostic shows two
visually identical lines.

## Two holes that remain open

**Hole 1 — an omitted compatibility description.** Deleting the 637 characters of Progress
DOM-structure prose that #635 adds leaves `check:release-note`, `check:release-note-coverage` and
`check:release-notes` all at exit 0. Coverage asserts that each consumed changeset *has its id listed*,
not that the prose says anything true or complete. #638 cannot close this: it compares note to page, so
it catches an alteration **after** activation, never an omission that was never written.

**Hole 2 — a published package changed with no changeset at all.** My own control, not in the brief:
appending one line to `packages/ui-angular/src/styles.css` with no changeset added leaves both
release-note gates at **exit 0**. The release suite has no check that a change to a *published*
package requires a changeset.

This is not hypothetical. Of the PRs in this phase's scope, **four touch published packages and carry
no changeset**:

| PR | published package touched | changesets |
|---|---|---|
| #631 | `packages/ui-angular` → @kinetixui/angular | **none** |
| #640 | `packages/ui-angular` → @kinetixui/angular | **none** |
| #642 | `packages/ui-angular` → @kinetixui/angular | **none** |
| #641 | `packages/ui` → @kinetixui/ui | **none** |

Each would ship a published-package change with **no version bump and no release-note entry**, and
nothing would object. By contrast #628/#629 (`ui-flutter`), #630 (`ui-compose`) and #633/#636/#637
(`ui-swiftui`) are correctly changeset-free: those packages are **never published to npm**.

Both holes are recorded as owner decisions rather than repaired here — see the owner register for the
proposed shapes and why each needs a control before it can be trusted.
