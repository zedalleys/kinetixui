### #634 closes the AudioPlayer defect

`readyState=4` means the browser has enough data to play to the end; `error=none` means no media error.
Both documented players report it. The control replaces the source with a cross-origin clip and both
drop to `readyState=0 error=4` (MEDIA_ERR_SRC_NOT_SUPPORTED), which is the original defect reproduced.
So the gate can tell a local playable clip from a foreign one the content policy refuses — it is not
asserting that an element merely exists.

## 5. Finding W1 — 9 of 12 header focus stops draw the browser's ring, not `--ring`

Measured on the composed candidate, so **neither #577 nor #583 changes this**. Each visible focusable in
`<header>` was focused in turn and its computed `outline` and `box-shadow` read:

| Theme | `--ring` | Stops | `outline-style: auto` (the UA ring) | Paints its own ring |
|---|---|---|---|---|
| light | `246 68% 56%` → `rgb(82, 67, 219)` | 12 | **9** | 3 |
| dark | `246 100% 85%` → `rgb(186, 179, 255)` | 12 | **9** | 3 |

The nine are the wordmark and the eight numbered nav links (`01 Docs` … `08 IoT`): all report
`outline: auto 1px rgb(16,16,16)` in light and `auto 1px rgb(238,238,238)` in dark, with `box-shadow:
none`. `outline-style: auto` is Chromium's own focus ring — the page is not painting it.

The three that do are `Search… Ctrl K`, `GitHub — 2 stars, 0 forks` and `Select theme`. They use the
token exactly, and they do not agree with each other:

```
GitHub        outline: solid 2px transparent   shadow: #fff 0 0 0 0, rgb(82,67,219) 0 0 0 2px
Search        outline: solid 2px transparent   shadow: rgb(82,67,219) 0 0 0 1px, rgba(82,67,219,.2) 0 0 0 4px
Select theme  outline: solid 2px transparent   shadow: rgb(82,67,219) 0 0 0 1px, rgba(82,67,219,.2) 0 0 0 4px
```

So the header has **three** focus treatments across twelve stops: the UA default on nine, a 2px token
ring on one, and a 1px token ring with a 4px translucent halo on two.

**Correction to my own first pass.** My initial probe classified these as 12/12 self-controlled, because
it treated any non-`none` outline as self-painted. `outline-style: auto` is the UA ring, so that
classification was wrong; re-measuring with that distinction reproduces the 9-vs-3 split exactly as it
was recorded in M5.12. The earlier M5.12 reading stands; this run confirms it on a newer tree.

This is **not a WCAG failure** — every stop has a visible focus indicator, and the UA ring meets contrast
on both backgrounds. It is a consistency defect, and no gate in the repository can see it: `check:footer`
measures the footer, `check:theme-isolation` measures the themed focus ring on the surfaces it covers,
and nothing walks the header.

## 6. Finding W2 — the Motion Lab has nothing to escape

§8 lists "Motion Lab Escape behaviour" as a priority. Measured on the candidate:

- The Motion Lab is **not a route**. It is `apps/web/src/components/motion-lab.tsx`, rendered as
  `<section id="motion">` on the homepage. That is why M5.12 got a 404 for it on every landable tree —
  there was no URL to land on, and there still is not.
- Inside it: `0` elements with `role="dialog"`, `role="alertdialog"` or `<dialog>`. It is a tab set, a
  disclosure button (`aria-expanded`), an email input with a live region, and two feedback buttons.
  There is no dismissible surface, so there is no Escape contract to meet.
- What Escape **must not** do is lose the reader's work. Probed by setting state (selecting the third
  tab "Settings", expanding the disclosure, typing `partial@` into the email) and then pressing Escape
  with focus on each of three owners in turn:

| Escape pressed from | selected tab | disclosure | email | focus still in the lab |
|---|---|---|---|---|
| the selected tab | Settings | true | `partial@` | yes |
| the disclosure button | Settings | true | `partial@` | yes |
| the email field | Settings | true | `partial@` | yes |

Nothing changed in any of the three. So the correct statement for the owner is that the item has no
implementation to verify, and the absence is benign — not that it passed a test.
