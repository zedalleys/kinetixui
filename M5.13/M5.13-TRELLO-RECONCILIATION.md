## How the updates were made, and why

Every M5.13 update was written as a **card comment**, not a description rewrite, with two exceptions
noted below. A comment cannot destroy what is already on the card, which is exactly what §11's
"preserve historical failed test evidence" asks for. Every write returned a `commentId` from the server
and is therefore a verified write, not a claimed one; one card was additionally read back in full to
confirm the comment had landed.

**No card was created.** All eleven items already had a home; the §11 list maps onto existing cards
once `#642` is read as belonging with `#640` and "final device certification" as belonging on the
long-standing Accessibility & QA register. Creating separate cards for those two would have been the
duplication §11 forbids.

**No card was closed, archived or marked done. No label was changed. No HOLD was altered.**

## One correction made during this phase

The first version of the comment on **#634** said that PR carried no changeset. It does —
`.changeset/audio-demo-ships-its-clip.md` — and it updates `release/notes/0.28.0.json` as well. The
error came from reading `gh api …/pulls/<n>/files`, which diffs a PR against **its own base branch**
rather than against `main`'s merge-base. The comment was edited in place, says at the foot that it was
edited and why, and the corrected version now names the five genuine instances of the
missing-changeset hole (#640, #641, #642, #631, #636) and explains that #632 only appears to be a sixth
because it inherits its changeset from #559's branch.

The same correction is applied in the Phase D report.
