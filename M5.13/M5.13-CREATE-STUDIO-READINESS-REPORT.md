## 1. §9's first question: the status of #574 on current main

**#574 is merged, by squash.** `gh api …/pulls/574` returns `state: closed`, `merged: true`,
`merged_at: 2026-11-14T21:32:37Z`, `merge_commit_sha: a8471a9aa4…`, base `main`.

The distinction matters and is the reason this phase has anything to report:

```
git merge-base --is-ancestor <#574 head 3106837c74> <main 6b1c990e>   → NOT an ancestor
git merge-base --is-ancestor a8471a9aa4…            <main 6b1c990e>   → IS an ancestor
```

A squash puts #574's *content* on `main` under a new commit and leaves its original head unreachable.
Every PR that was stacked on #574's branch therefore carries that content a second time, and shows up as
conflicting — which is exactly the pattern in §3.

## 4. Does #616 remain preferred? Yes, and the fix is not the discriminator

The component repair is **byte-identical** in all three repair PRs. SHA-256 of the whole file
`apps/web/src/components/create-studio/viewport-preview.tsx` at each head:

```
#616  1b665cbc78d032517e7b650f9b2353cd643254111b9c1de02f568c86f3ffec8a
#600  1b665cbc78d032517e7b650f9b2353cd643254111b9c1de02f568c86f3ffec8a
#603  1b665cbc78d032517e7b650f9b2353cd643254111b9c1de02f568c86f3ffec8a
```

Each adds the same +30/−0 hunk: a `React.useEffect` that redefines `activeElement` as an own property
on the **host** document for the life of the preview, so that while the host's active element is the
preview `<iframe>`, the getter returns the *frame's* active element instead. The cleanup `delete`s the
own property and restores the platform getter.

That is the realm-boundary diagnosis, and the comment in the hunk states its scope correctly: it affects
every roving-focus group portalled into the frame, not only Tabs, and it is a property of portalling
into a frame rather than a defect in `@kinetixui/ui`. Nothing in this phase contradicts that.

So the choice between #616, #600 and #603 is **not** a choice between fixes. It is a choice of lineage,
and only #616's lineage is current:

| | #616 | #600 | #603 |
|---|---|---|---|
| Same component fix | yes | yes | yes |
| Restacked onto post-squash `main` | **yes** | no | no |
| Contains #576's current head | **yes** | no | no |
| Conflicts vs `main` | **0** | 6 | 6 |
| Also updates the gate | yes (+32/−0) | yes (+25/−12) | yes (+25/−0) |
| Also wires the workflow | yes (+1) | **no** | yes (+1) |

#600 is the weakest of the three on paper: it alone omits the `create-studio.yml` line, so its gate
addition would not run, and its base branch is a third-party thread branch rather than #576's.

**#599 is different in kind.** It changes no component code at all — only
`scripts/create-studio-responsive-browser.mjs` (+18/−2) and the workflow (+1). It is a gate change
without a repair, so on a tree that still has the defect it would assert the defective behaviour. The
M5.12 finding stands: a Chromium A/B on two built heads showed #616 restores clean-document tab entry,
which makes #599's `Tab → Details` assertion false. Re-examining it here does not change that, and
#599 is additionally six conflicts stale.
