# Search intent map

**Supporting document.** One primary search intent per route, so pages stop competing with each other. Wording
follows [`../MESSAGING.md`](../MESSAGING.md) and [`../CLAIMS.md`](../CLAIMS.md); clusters come from
[`../seo.md`](../seo.md). The titles and descriptions that implement this map live in
[`apps/web/src/lib/route-seo.ts`](../../apps/web/src/lib/route-seo.ts) (non-component pages) and are generated by
`componentMetadata` in [`apps/web/src/lib/seo.ts`](../../apps/web/src/lib/seo.ts) (component pages).

**No search-volume numbers appear here.** None were measured: there is no keyword tool connected to this
repository, and Search Console is not set up yet ([`MEASUREMENT.md`](./MEASUREMENT.md) §5). The families below are
the questions the product genuinely answers; which of them bring traffic is what the first eight weeks of Search
Console data will say. Revisit this map then.

**How to read it.** *Primary* is the one intent the page's title and H1 are written for. *Secondary* intents may
appear in the description or body, but another page owns each of them as its primary. A query family with no owner
is in the "unowned" table at the end, on purpose.

### Collisions this map resolves

- **Homepage vs `/components` vs `/docs/platforms`.** All three used to say "React, Angular, SwiftUI, Compose and
  Flutter". The homepage now owns the *category* ("cross-platform design system infrastructure"), `/components`
  owns *components for the five platforms*, and `/docs/platforms` owns *coverage/parity*.
- **`/docs/tokens` vs `/docs/theming` vs `/docs/foundations`.** Tokens owns "design tokens across platforms",
  theming owns "retheme with semantic tokens", foundations owns the non-colour scales.
- **`/iot` vs `/docs/iot`.** The showcase owns the category query; the docs page owns the package.
- **Platform pages vs each other.** Each title names one platform and its real distribution state, derived from the
  manifest, so the four pages are not one template with the name swapped: Angular says "preview" and "npm"; the
  native pages say "source you build today, not yet on <channel>".
- **ART-001 vs `/docs/platforms`.** See below.

## ART-001 alignment

ART-001, *"Your cross-platform design system may be lying about parity"*, publishes on dev.to on **Tue 13 Oct**
(not in this workstream).

- **Canonical destination.** One kinetixui.com link: `/docs/platforms`, tagged
  `utm_source=devto&utm_medium=referral&utm_campaign=kx_p1_a_parity_proof&utm_content=art_primary`, matching
  `marketing/content/register.json` byte for byte. That follows the existing campaign convention and is correct.
- **Does it compete with `/docs/platforms`?** No. The article's intent is an *opinion/awareness* query ("is my
  cross-platform design system's parity real?"); `/docs/platforms` owns the *evaluation* query ("what does this
  library actually cover per platform"). The article links to the page; the page does not need to rank for the
  article's headline.
- **The tagged link and the canonical.** The UTM-tagged URL now resolves to a page whose canonical is the clean
  `/docs/platforms` (this workstream), so dev.to's link does not create a second indexable URL.
- **Deeper links.** The package has one kinetixui.com link today, which is within the brief ("one or two deeper
  pages only"). If a second link is wanted after publication, the strongest is `/docs/components/direction-provider`
  — the component the story is about — tagged with the same campaign and `utm_content=art_story`. Recommendation:
  **do not change the package before Tuesday**; add it in the post-publication close-out if at all.
- **Article canonical.** The article stays canonical on dev.to (as ART-002 is); there is no `/blog` to point at.
